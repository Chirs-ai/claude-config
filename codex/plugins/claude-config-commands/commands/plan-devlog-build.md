结合当前会话上下文和用户输入，先沉淀可执行方案，再保存到 `devlog/`，完成方案自评，确认无阻塞问题后开始实施。

方案或需求内容：$ARGUMENTS

---

## 阶段一：上下文归纳

1. 回顾当前会话中最近的需求、约束、方案讨论和用户偏好
2. 搜索并阅读相关源文件，理清现有数据结构、调用链、渲染逻辑和测试方式
3. 将上下文整理为明确的问题定义、目标、非目标和验收标准
4. 如上下文不足以判断实施路径，先提出需要用户澄清的问题并暂停

## 阶段二：详细方案

1. 给出可执行方案，列出涉及的文件、函数、数据结构和关键改动
2. 说明边界情况、兼容性、失败路径和回归风险处理
3. 评估改动量级和验证方式
4. 判断结论：可实施 / 有条件实施 / 不建议实施
5. **不建议实施或有条件实施且条件不明确时，暂停并向用户说明原因**

## 阶段三：写入 devlog

1. 通过 `date '+%Y-%m-%d-%H%M'` 获取实际当前时间
2. 如果项目 `devlog/` 目录不存在，创建它
3. 创建文件名：`YYYY-MM-DD-HHMM-语义描述.md`
   - 语义描述使用小写英文短横线连接
   - 名称应概括方案主题，而不是命令名称
4. 将上下文归纳、详细方案、影响范围、风险评估和验证计划写入 devlog

## 阶段四：方案自评

1. 搜索所有会受改动影响的调用点、入口、测试和配置
2. 检查函数签名、返回值、状态流、数据流、权限和错误处理是否会破坏现有行为
3. 对照 devlog 检查方案是否完整、可执行、可验证
4. **发现设计缺陷时，先修正方案并更新 devlog，再继续**
5. **存在无法自证的高风险或不确定点时，暂停并向用户说明**

## 阶段五：实施

1. 自评通过后直接按 devlog 方案实施，不再额外等待确认
2. 实施过程中如发现方案需要调整，先更新 devlog，再继续修改代码
3. 保持改动范围贴合方案，不引入无关重构

## 阶段六：自检与验证

1. 重新审查所有改动，重点检查边界情况、空值处理、回归风险、性能和兼容性
2. 运行相关测试、构建、lint 或可行的手工验证
3. 测试失败时先修复，再重新验证
4. 最终向用户汇报 devlog 路径、关键改动和验证结果

---

## 流程控制原则

- 这个命令适合用户已经给出方案、想法或上下文，并希望 Claude/Codex 整理成正式实施方案后直接推进
- 默认不提交代码，除非用户同时明确要求提交、推送，或另行调用 `/gitpush` 或 `$gitpush`
- 遇到破坏性操作、生产环境操作、数据迁移、删除数据、凭据变更或不可逆操作时，必须暂停并请求用户确认
- 输出保持简洁，但 devlog 内容要足够让后续会话接续工作
